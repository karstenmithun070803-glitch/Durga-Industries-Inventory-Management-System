## 1. What We're Building

A **real-time, web-based inventory and billing management system** for **Durga Industries**, a bus/vehicle body manufacturing company. They currently use a legacy Windows desktop ERP (BillPlus GST V2.0.5) which is difficult to use, has no proper inventory tracking, and is not accessible on multiple devices.

**Core goals:**
- Modern, simplified UI — easy for non-technical staff to use
- Real-time stock tracking: materials enter stock via Purchase Orders, exit stock via Vehicle Job allocations
- GST-compliant invoicing (both CGST+SGST for intra-state and IGST for inter-state)
- PDF generation for Purchase Orders, Delivery Challans, and Invoices
- Accessible on any device (web app), synced in real-time
- 100% mathematical accuracy — no manual stock edits allowed

**What the business does:** They build bus bodies. They buy raw materials (steel angles, glass, rubber, paint, etc.) from suppliers. Those materials are allocated to specific vehicle jobs. When a vehicle is complete, they invoice the customer (often an insurance company).

## 2. Tech Stack

| Layer | Technology | Cost |
|---|---|---|
| Frontend | Next.js 14 (App Router) + TypeScript | — |
| UI Components | Tailwind CSS + shadcn/ui | Free |
| Backend/DB + Realtime | Supabase (PostgreSQL + built-in WebSocket realtime) | Free tier (500MB, 200 concurrent connections) |
| ORM | Drizzle ORM (type-safe, strict FK constraints) | Free |
| Deployment | Cloudflare Workers via OpenNext adapter | Free / ~$5/mo |
| PDF Generation | @react-pdf/renderer | Free |
| Auth | Supabase Auth (username → internal email mapping) | Free |

**Why Cloudflare Workers (not Vercel):** Vercel Hobby ToS explicitly prohibits commercial use. Cloudflare Workers free tier allows commercial use with unlimited team members.

**Why Supabase (not Neon):** Real-time WebSocket sync is a core requirement. Neon has zero built-in real-time; Supabase has it free. Supabase free tier is safe for daily use (pauses only after 7 consecutive days of zero database activity — not a concern for a business using it daily).

**Auth — username login (not email):**
- The login screen shows only a **username** field (e.g. `mithun`, `owner`) — no email field visible to users
- Server maps username → internal technical email (e.g. `mithun@durgaindustries.internal`) stored in a `app_users` table
- Calls Supabase Auth with that technical email + password
- All user accounts are created manually by the developer (no self-registration)
- Max 4 users

**Database rules:**
- All PKs are UUIDs
- All human-facing IDs (PO number, slip number, job no, bill number) are auto-incrementing integers displayed as formatted strings
- All inventory math happens server-side (Supabase DB transactions or Next.js API routes) — NEVER client-side math for stock

### 4.2 Purchase Orders

**Purpose:** Record materials purchased from suppliers. When a PO is marked as received (Purchase Inward), stock increases.

**Simplified from old software:** The old "PO Gen (Material List)" + "Purchase Order" are combined into ONE tab.

**Header fields:**
- PO Number (auto-assigned, e.g. "PO-0042")
- PO Date (date picker, defaults to today)
- Supplier (dropdown — pulls from Supplier Master; shows name + GSTIN)
- Supplier Address (auto-filled)
- Total Amount (auto-calculated, displayed prominently)
- Status (Draft / Received) — when set to "Received", triggers stock addition

**Line item table (repeating rows):**
- S.No (auto)
- Material No (auto-filled when material selected)
- Material Name (searchable dropdown from Material Master)
- Qty (number)
- Unit (auto-filled from Material Master)
- Rate (number — price per unit)
- Tax % (auto-filled from Material Master, overridable)
- Tax Amount (calculated)
- Amount (calculated: qty × rate)

**Actions:** Add Row, Delete Row, Save as Draft, Mark as Received, Print PDF, Export

**Inventory trigger:** When Status changes to "Received":
- For each line item: `material.current_stock += qty`
- This is an atomic DB transaction — if any line fails, all revert
- If a received PO is edited, the old stock addition is reversed and the new one applied
- If a received PO is deleted, the stock addition is fully reversed

**Print output:** Supplier-wise PO PDF with company header, supplier details, line items, total, tax breakup (CGST+SGST or IGST based on supplier state vs company state Tamil Nadu)

## 5. Business Rules (Critical — Must Be Enforced in Code)

### 5.1 Inventory Engine (Triple-Trigger, No Direct Edits)
- `current_stock` is **NEVER directly edited by any user** through a form
- Stock changes through **three defined triggers only**:
  1. **INCREASE:** Purchase Order marked as "Received" → adds qty per line item
  2. **DECREASE:** Material Issue saved → subtracts qty per line item (only `affects_inventory = TRUE` rows)
  3. **ADJUSTMENT:** Manual Stock Adjustment → corrects physical vs digital discrepancies
- All three are atomic DB transactions (all succeed or all fail)
- Edit/Delete of a received PO or saved DC must reverse and reapply stock atomically

**Manual Stock Adjustment — UX:**
- Accessible from Stock Dashboard only
- Required confirmation modal with this text:
  > "⚠️ WARNING: Manual Stock Adjustment. You are about to directly override the system stock count. This bypasses the normal purchase and issue workflow. Use this ONLY for: physical audit discrepancies, damaged goods, lost/stolen materials. This action is permanent and will be recorded in the stock ledger with your name, the timestamp, and your reason. Type CONFIRM in the box below to proceed."
- Confirmation input must match "CONFIRM" exactly (case-sensitive)
- Required fields: Material, Adjusted Qty (+/−), Reason (minimum 10 characters)
- Stock cannot be adjusted below 0 (hard block)

### 5.2 GST Logic — GSTIN-First Determination
- Company state: Tamil Nadu (state code **33**)
- Tax type determined by **first 2 digits of Customer/Supplier GSTIN** — NOT the state dropdown
  - "33" → CGST (50%) + SGST (50%)
  - Anything else → IGST (100%)
- Fallback: if no GSTIN (blank or "URP"), use state dropdown
- System displays "CGST+SGST" or "IGST" badge so user can verify before saving

### 5.3 Invoice — Dual PDF (Same Net Amount in Both)
- Both PDFs must show the **exact same Net Amount** — the Customer PDF cannot alter the total
- System auto-determines CGST+SGST vs IGST via GSTIN-first rule

### 5.4 Contractor Tracking
- Assigned **per material line item** in Material Issue — NOT at the job level
- Different contractors handle different materials on the same job
- `contractor_id` in `material_issue_items` is optional
- Job search output shows: Material | Qty | Unit | Rate | Amount | Contractor

### 5.5 Auto-Assigned Numbers — Financial Year Reset & Concurrency Safety
- Bill Numbers, PO Numbers, Issue Slip Numbers **reset to 1 on April 1 each year**
- Master record codes (Material No, Supplier Code, etc.) do NOT reset
- Uniqueness constraints: `UNIQUE(po_number, financial_year)`, `UNIQUE(slip_number, financial_year)`, `UNIQUE(bill_number, financial_year)`
- All numbers generated by **PostgreSQL SERIAL / sequences** — never in application code (prevents race conditions)

Document formats:
- PO Number: `PO-XXXX` | Issue Slip: `IS-XXXX` | Bill Number: `[inv_prefix]-XXXXXXX` | Job Ref: 5-digit (01963)

### 5.6 Financial Year — Historical Year Warning Banner
- Financial year: April 1 → March 31 (India standard)
- When viewing any non-current year: persistent non-dismissable amber banner on every page:
  > "📅 Viewing Historical Data — FY 2024-2025. All new entries will be saved to this year. Switch back to current year to resume normal operations."

## 6. Database Schema (Key Tables)

### Schema Architecture Rules
1. **PKs:** Every table `id UUID DEFAULT gen_random_uuid()`
2. **Display IDs:** SERIAL fields are human display only, never used in JOINs
3. **Soft Deletes:** `is_active BOOLEAN DEFAULT TRUE` on all Master tables
4. **Timestamps:** `created_at` AND `updated_at` on every table
5. **GST Split:** All transaction item tables store `cgst_amount`, `sgst_amount`, `igst_amount` separately
6. **Historical Tax Lock:** All item tables store `tax_percentage` at time of entry

```sql
-- MASTER TABLES
customers (id UUID PK, customer_name, address_1, address_2, street, city, state, gstin, is_active, created_at, updated_at)
contractors (id UUID PK, code_no SERIAL UNIQUE, name, role, contact, is_active, created_at, updated_at)
suppliers (id UUID PK, code_no SERIAL UNIQUE, name, tin_no, cst_no, gstin, address, state, is_active, created_at, updated_at)
tax_rates (id UUID PK, vat_code SERIAL UNIQUE, tax_percentage, description, inv_prefix, is_active, created_at, updated_at)
units (id UUID PK, unit_code SERIAL UNIQUE, unit_name, is_active, created_at, updated_at)
materials (id UUID PK, material_no SERIAL UNIQUE, name, hsn_code, tax_rate_id FK, purchase_unit_id FK, sales_unit_id FK, conversion_value, opening_stock, current_stock CHECK(>=0), min_level, max_level, is_active, created_at, updated_at)
vehicles (id UUID PK, job_ref_no SERIAL UNIQUE, vehicle_name, type CHECK('New'|'Old'), customer_id FK, is_active, created_at, updated_at)
app_users (id UUID PK, username UNIQUE, supabase_auth_id UUID UNIQUE, display_name, created_at, updated_at)

-- TRANSACTION TABLES
purchase_orders (id UUID PK, po_number SERIAL, po_date, supplier_id FK, total_amount, status CHECK('Draft'|'Received'), financial_year, created_at, updated_at)
  -- UNIQUE(po_number, financial_year)

purchase_order_items (id UUID PK, po_id FK CASCADE, material_id FK, qty, unit_id FK, rate, tax_percentage, cgst_amount, sgst_amount, igst_amount, amount, created_at, updated_at)

material_issues (id UUID PK, slip_number SERIAL, issue_date, vehicle_id FK, margin_percentage, total_amount, financial_year, created_at, updated_at)
  -- UNIQUE(slip_number, financial_year)

material_issue_items (id UUID PK, issue_id FK CASCADE, material_id FK, hsn_code, qty, unit_id FK, rate, tax_percentage, cgst_amount, sgst_amount, igst_amount, amount, contractor_id FK NULL, affects_inventory BOOLEAN DEFAULT TRUE, created_at, updated_at)

invoices (id UUID PK, bill_number TEXT, bill_date, rate_date, tax_percentage, material_margin, discount, vehicle_id FK, net_amount, rev_charge_status BOOLEAN, financial_year, created_at, updated_at)
  -- UNIQUE(bill_number, financial_year)

invoice_items (id UUID PK, invoice_id FK CASCADE, material_id FK, hsn_code, qty, unit_id FK, rate, tax_percentage, cgst_amount, sgst_amount, igst_amount, amount, created_at, updated_at)

-- STOCK LEDGER (immutable — never update or delete rows)
stock_ledger (id UUID PK, material_id FK, transaction_type TEXT NOT NULL, reference_id UUID, reference_type TEXT, qty_change NUMERIC, stock_after NUMERIC, reason TEXT, adjusted_by TEXT, created_at)
  -- transaction_type validated in app layer (not DB CHECK) for extensibility
  -- current values: 'PO_INWARD' | 'ISSUE' | 'REVERSAL' | 'ADJUSTMENT'
```

## 7. UI / UX Principles

> **Component rule:** Use **shadcn/ui** exclusively. `<Command>` for searchable dropdowns, `<Toast>` for feedback, `<Dialog>` for destructive confirmations. Compact tables with sticky headers.

### 7.1 Data Entry (Speed Is King)
- All dropdowns use shadcn `<Command>` combobox (type to search)
- Tab = next cell, Enter on last cell = new row (keyboard-first transaction tables)
- Smart auto-fill: Material → Unit/HSN/Tax %, Job No → Vehicle/Customer/GSTIN, Rate → last PO price
- Date fields default to today
- Sticky Save/Cancel bar + Grand Total at bottom of viewport (never scroll to save)
- Inline row deletion (trash icon, no modal for individual line items)

### 7.2 Data Display (High Density)
- Compact table layouts (minimal padding — factory/accounting use)
- Sticky table headers
- Key figures in large bold text; secondary info in muted gray
- Status badges: Draft=Gray, Received/Saved=Green, Cancelled=Red, Low Stock=Yellow/Orange
- Sortable columns, pagination or virtual scroll on large lists

### 7.3 Feedback & Safety
- Toast on every save/edit/delete/error
- Destructive actions (delete document): `<Dialog>` modal with explicit stock reversal warning + red confirm button
- Double-submit prevention: Save button disables + spinner on first click
- Inline field validation with red highlight + helper text on specific failing field
- Stock conflict warning inline on the row: "Only 3.5 KG available in stock"

### 7.4 Navigation & Layout
- Minimal sidebar: Dashboard | Masters | Transactions | Invoice | Reports | Settings
- Breadcrumbs on every page: e.g. `Masters > Materials > Edit: 25*3MM Angle`
- Dashboard + Reports: fully responsive (owner checks on phone)
- Transaction entry (Invoice, PO): desktop-only is acceptable
- Historical year: persistent non-dismissable amber full-width banner on every page

### 7.5 Print & PDF
- Standard Indian GST invoice format (company header, bill-to, line items, tax summary, total in words)
- Download + Print button on every record's own page (not just in Reports)
- Min 10pt font for A4 print readability
- 25+ line items: overflow to page 2 with column headers repeated; total section always on last page

## 8. Edge Cases & Defensive Programming (Must Implement All)

### 8.1 Inventory Math
- **Negative stock: Hard block** — check entire Material Issue before saving. If any line item would cause negative stock, reject all. Never store `current_stock < 0`. Add DB constraint `CHECK (current_stock >= 0)`.
- **Min/Max: Soft warning** — toast but allow save
- **Zero rate: Soft block** — yellow highlight, tooltip "No purchase history. Enter rate manually." Hard block save unless user checks "I confirm zero cost."
- **Manual adjustment: Cannot create negative stock**

### 8.2 Master Data
- Soft-deleted items hidden from dropdowns but still render in historical documents (`LEFT JOIN`, not `INNER JOIN`)
- Conversion value changes apply to future transactions only — historical records keep their saved snapshot
- Duplicate name: soft warning toast (not hard block)

### 8.3 Invoice & Tax
- **Rounding: Line item first** — round `cgst_amount`, `sgst_amount`, `igst_amount` at line item level; Grand Total = SUM of rounded items (prevents 1-paisa mismatch)
- **Discount > total: Hard block** — Net Amount cannot be negative or zero
- **Cross-year date: Hard block** — `po_date`, `issue_date`, `bill_date` must fall within active financial year
- **Reverse charge**: alert user "Reverse Charge invoices must not show CGST/SGST/IGST. Confirm this is correct."
- **GSTIN validation**: pattern `^\d{2}[A-Z]{5}\d{4}[A-Z]{1}[A-Z\d]{1}[Z]{1}[A-Z\d]{1}$`, validate on blur, warn if first 2 digits mismatch selected state

### 8.4 Purchase Orders
- **Partial shipments**: edit PO qty to actual received, mark as Received. Create new Draft PO for remainder.
- **Editing received PO**: confirmation dialog + atomic reverse+reapply
- **Deleting received PO**: explicit modal listing what stock will be removed. Hard block if any stock has already been issued to jobs.

### 8.5 Financial Year
- Switching years with unsaved form: modal "You have unsaved changes. Switching will discard entry. Continue?"
- Year-end carry-forward: `current_stock` carries forward automatically (does not reset to opening_stock)

### 8.6 Network & Concurrency
- Double-submit: disable button + spinner on first click; re-enable on error
- Simultaneous edit conflict: Postgres transaction failure → toast "Save failed: record modified by another user. Refresh and try again."
- Session timeout: intercept 401, redirect to login, attempt to restore form state from `sessionStorage`

### 8.7 PDF
- 25+ line items: overflow to page 2 with repeated headers; totals always on last page
- Special characters (`&`, `"`, `%`) escaped correctly in PDF renderer
- Offline: toast "PDF generation requires an internet connection"

## 9. Modularity Guidelines

### Adding a New Master Tab
1. Create `/src/app/(dashboard)/masters/[new]/page.tsx`
2. Create `/src/lib/actions/[new].actions.ts`
3. Add table to `/src/db/schema.ts`, run `drizzle-kit migrate`
4. Add sidebar nav link

### Adding a New Transaction Tab
1. Create `/src/app/(dashboard)/transactions/[new]/page.tsx`
2. Create `/src/lib/actions/[new].actions.ts`
3. If affects stock: add new string to `StockLedgerType` enum in `/src/types/index.ts` (no DB migration needed)
4. Reuse `<TransactionGrid />` and `<MasterLayout />`

### Removing/Hiding a Tab
- Remove nav link only — never delete route or table that has historical data

### What Always Requires DB Migration
- Adding/removing columns, adding new tables, changing FK relationships

### What Never Requires DB Migration
